# 开发任务：手绘赛道 · 2D 玩具赛车

请在当前已授权的项目目录中，直接实现一个本地可运行、可实际游玩的网页游戏 MVP。先检查目录和适用的 AGENTS.md；已有项目沿用其兼容的技术约定，空目录再初始化。下面是完整需求，不依赖之前的聊天记录。请持续推进到实现、浏览器试玩和必要检查完成，不要只交付方案、静态效果图或按钮无法操作的页面。

## 1. 项目背景与已经确定的方向

用户熟悉前端、Node.js、NestJS，以及基础 Go 开发，希望通过 vibe coding 做一个自己也愿意玩的完整小作品。

已经确定的玩法是：

鼠标画一条首尾相连的线 → 生成有宽度的赛道 → 玩家用键盘实时驾驶小车 → 完成一圈并挑战自己的最快成绩。

第一版采用固定俯视角的 2D 画面。画线决定道路形状，车辆的加速、刹车、转向由玩家控制。赛车不自动沿着线行驶。

已知 Apex Drawn、Warp Racer 等有相近玩法。我们接受同类型作品的存在，当前目标是完成一个手感舒服、视觉统一、可以自行画赛道的个人作品，不宣称玩法首创，也不以复制其全部功能为目标。

以下决定已经确认，无需再次询问：2D、PC 浏览器优先、单人、本地保存、手动驾驶、手绘方格纸画风、运行时不接 AI 模型。React/Vue 等常规实现选择可结合当前工程自行决定。

## 2. 首版交付范围

必须完成：

- 一张默认示例赛道，用户打开游戏即可开始驾驶。
- 鼠标自由绘制一条闭合赛道；有效性检查、失败原因提示、重新绘制、取消绘制。
- 一辆具有加减速、转向和轻微惯性的赛车。
- 离开道路后明显减速，可以继续开回道路。
- 开始、暂停、继续、重新开始；有效圈速判定和个人最快成绩。
- 当前赛道与对应最快成绩的本地保存，刷新后可恢复。
- 下面约定的完整画风、游戏 HUD、关键交互反馈。
- 可运行工程、清楚的启动说明、真实浏览器验证与必要的核心规则测试。

本次不包含：3D、AI 对话或生图接口、联网对战、后端服务、账号、支付、公开排行榜、赛道社区、幽灵车、车辆改装、多种车型。未来有需要再扩展，本次仅保留清楚的数据边界，不提前搭建平台或插件系统。

### 3.1 整体观感

主题是“方格本上的玩具赛车”：轻松、干净、带一点手绘质感。场景是一张纸，玩家像在本子上画好道路，再开一辆玩具车。

- 背景：浅米色方格纸，纸纹轻淡，网格低对比。
- 道路：灰色铅笔涂绘质感，有清晰的宽度，边缘轻微不规则；道路中心虚线柔和。
- 小车：橘红色车身、深色轮胎、浅色车窗。严格俯视、比例明确，车头方向始终容易辨认。
- 点缀：少量蓝灰色手绘树、草、石头和路锥；装饰位于道路以外，保持驾驶区域干净。
- 配色参考：纸色 #F2E7D1、网格 #C5CCD0、墨色 #374553、强调色 #D65932、道路 #A6A3A0。根据参考图微调，统一收进设计变量。

避免做成后台管理界面或营销落地页。画面主体是可以游玩的赛道，不是大标题、指标卡片和功能说明。

### 3.2 素材与绘制

把纸张背景、道路、车、装饰、轮胎痕迹、HUD 分层实现。

- 背景、道路和简单装饰优先使用程序绘制、SVG 或生成纹理，便于匹配任意玩家赛道。
- 小车可以用精细的程序绘图、SVG 或透明贴图。统一线条、颜色和阴影即可，不要求依赖额外生图服务。
- 如果环境有可用的生图能力，可以用于开发阶段的单独素材制作；生成后纳入本地资源。缺少该能力时继续用代码完成一致的美术。
- 不把整张概念图当作游戏背景来假装可玩，也不从整图裁出自带方格纸背景的小车。
- 碰撞和道路判定使用稳定的几何数据；铅笔纹理和轻微手绘抖动只作用于外观。
- 装饰按固定种子生成，设置道路避让距离和有限尝试次数；重新绘制一条赛道后再生成装饰，不在每一帧随机变化。

### 3.3 UI 和反馈

- 左上：简短模式标签，如“自由试跑”。
- 上方：本圈时间、个人最佳；右上：暂停。
- 下方：编辑赛道、重新开始，以及一行简短的操作提示。
- 按钮是轻微纸片质感，清楚区分普通、主操作、禁用、悬停和按下状态。
- 正文与数字清楚可读；字体可以圆润，但不要为了手写感牺牲中文可读性。
- 拖画过程中立即显示路线；错误片段有可见提示。
- 赛车可有少量轮胎痕迹和灰尘，效果数量受限、及时回收。
- 刷新个人纪录时出现短暂的小印章或轻量动画，不遮挡后续驾驶。
- 音效只在用户交互后启用；提供静音操作。音效失败不影响游戏。
- 玩家界面不暴露采样点数量、法线、阻尼、调试包围盒等实现参数。开发调试信息放在可关闭的开发入口中。

## 4. 玩家流程与交互

### 4.1 打开和驾驶

打开后立即呈现一张可玩的默认赛道和清楚的“开始”操作。短提示说明：↑/W 加速，↓/S 刹车，←/A 与 →/D 转向，R 重新开始，Esc 暂停。

开始后将游戏区域置于可接收键盘输入的状态；在游戏区域内处理方向键的默认滚动。在输入框中或游戏不活跃时，不全局抢占键盘。刹车把前进速度降到零，首版可以不做倒车。

暂停时车辆和计时一起暂停。切出窗口、浏览器标签隐藏或失去焦点时清空按键状态并暂停；用户明确继续后恢复，避免卡住油门或恢复时车辆跳跃。

R 和“重新开始”恢复到起点、起始方向与零速度，清空当前圈的进度与有效性状态，保留该赛道最快成绩。

### 4.2 编辑赛道

点击“编辑赛道”暂停驾驶并保留旧赛道，显示简洁的绘制操作。

- 鼠标按下开始采样，拖动显示连续线条，松开进行检查。
- 首尾足够接近时吸附闭合；距离过大时提示“请将终点画回起点附近”，不偷偷用一条很长的直线强行闭合。
- 路线有效后显示真正有宽度的道路，并提供“开始试跑”和“重新绘制”。
- 路线无效时保留可见草稿，说明问题，例如“这里发生交叉”“这个弯太挤”，让玩家重画。
- 取消编辑恢复旧赛道。无效草稿不能覆盖有效赛道或对应存档。
- 第一版只需要单条闭合路线和重新绘制；控制点编辑、分段宽度和复杂编辑工具属于后续扩展。

## 5. 赛道几何与绘制规则

赛道的权威数据是中心线、道路宽度和版本信息。显示、道路检测、起点、检查点都从同一套数据派生。

推荐处理链：

原始指针坐标 → 转换为游戏世界坐标 → 去重、去掉过密点 → 简化 → 闭合和平滑 → 按弧长重采样 → 校验最终道路 → 生成绘制与计时数据。

- 世界坐标独立于屏幕尺寸。屏幕缩放、画布尺寸、留白和 devicePixelRatio 不能改变赛道形状或驾驶规则。
- 采样点与最终点数设置合理上限，避免长时间拖画造成卡顿。
- 路线需要足够长，闭合后有可驾驶的内部空间。
- 第一版采用固定道路宽度，不支持交叉道路、立交桥和道路自重叠。
- 平滑可能产生新的交叉，必须校验最终中心线和有宽度的道路，不只检查原始输入线。
- 检查非邻近路段的距离，避免中心线没相交但道路边缘已经挤在一起。局部邻近的判定依据沿线距离，而不是固定跳过几个点。
- 极尖转角或无法容纳道路宽度的区域，可以保守拒绝，并给玩家可理解的提示。
- 默认赛道应容易驾驶，至少包含直道、缓弯和一个需要减速的弯，适合测试手感。

## 6. 车辆运动与手感

采用适合 2D 俯视赛车的简化运动模型。Phaser 负责场景、绘制、输入等；车辆运动用独立的 TypeScript 逻辑管理即可，首版不要求引入完整刚体汽车模拟。

基本状态包括位置、车头朝向和速度。实现可调的加速度、刹车减速度、最大速度、转向响应、前进阻力和横向阻尼。

- 按油门逐渐加速，松开后逐渐减速。
- 转向与速度有关；车辆静止时不原地高速旋转。
- 有轻微惯性和可控制的侧滑，首版不要调成难以收回的持续漂移。
- 道路外区域阻力更大、目标速度更低；开出去后仍能操作回道路。
- 外边界提供恢复办法，车辆不会永久消失在画面外。
- 使用固定模拟步长或等效的稳定积分策略，渲染帧率不决定车辆速度和圈速。暂停、恢复及较大帧间隔要有明确处理。
- 所有手感参数集中配置，便于根据试玩反馈调整，不在多个组件里散落魔法数字。

用矩形占位车先验证这些行为，再替换正式美术。

## 7. 计圈与成绩规则

完成一圈需要按正确方向穿过起点线，且按顺序通过沿赛道布置的检查点。不能通过倒车跨起点、在起点附近来回移动，或直接横穿内场刷新成绩。

- 起点方向由起点处的路线切线确定。
- 起跑与完成一圈的状态明确区分，第一次驶离起点不会误记为完成。
- 使用上一帧到当前帧的移动线段判断过线，避免车辆较快时跳过检测。
- 检查点按顺序推进，并位于道路范围内；不能只根据“离起点很近”认定完成一圈。
- 车辆中心明确离开道路的该圈标为无效，显示“本圈不计成绩”；可以继续驾驶。走完路线回到起点后，开始新的有效圈。
- 道路边界的容差统一配置，让显示与判定相符；轮胎轻微接触铅笔边缘不应产生难以理解的处罚。
- 暂停不累计时间；重新开始清零当前圈。
- 只有有效圈能更新最快成绩。完成一圈后可继续下一圈，同时短暂显示上圈成绩。
- 时间计算与屏幕上数字刷新分离，最终成绩使用可靠的游戏计时数据。

## 8. 存档与数据边界

采用浏览器本地存储。数据规模小可以使用 localStorage，需要更多结构时再选 IndexedDB。至少保存当前有效赛道、该赛道最快成绩和声音偏好。

赛道使用可序列化格式，包含 schemaVersion、稳定 ID 或几何指纹、中心线控制点、道路宽度及必要元数据。检查点、绘制缓存等派生数据尽量重建。

修改赛道后重新确定成绩归属，不能把旧赛道的最快时间直接当作新赛道纪录。必要时把影响手感的规则版本纳入成绩归属。

读取存档时校验版本、类型、点数、数值是否有限以及几何有效性。存档损坏或存储不可用时使用默认赛道并保持可玩，不能白屏。绘制过程不逐帧写存储，只保存有意义的完成状态。

## 9. 技术实现约定

新项目默认采用 Vite + TypeScript + Phaser，界面可用 React 或 Vue，优先选当前项目已经使用的框架。依赖版本、模板和官方文档使用同一主版本体系，并提交锁文件；不要把不同大版本示例混在一起。

建议把代码分成几类职责：

- 赛道几何与校验：尽量是无 DOM、无引擎依赖的纯逻辑。
- 车辆运动与计圈：输入明确、可单独验证的规则。
- 游戏场景：渲染、镜头、引擎对象和输入适配。
- UI：模式切换、按钮、时间、提示、设置。
- 存档和资源：序列化、恢复、美术与音效加载。

目录命名自行贴合项目规模。保持简单直接，不为了这些分类搭建复杂框架。

不要让每帧的赛车位置触发整个 React/Vue 页面重渲染。静态赛道、纸张网格和装饰应缓存；清理引擎、事件监听器、粒子和资源，避免热更新或反复开始后叠加多个游戏循环。

## 10. 开发顺序与阶段完成条件

按下面顺序完成整个 MVP。阶段完成是进入下一阶段的检查点，不是停下来等待用户确认的理由。沿用已经确认的需求，常规工程选择自行处理；只有缺少必要信息、权限或外部资源且无法替代时再说明阻塞。

阶段 A：固定赛道驾驶。
完成条件：默认赛道上可开始、加速、刹车、转向、出界减速、暂停与重置；失焦安全恢复；车辆没有明显异常跳跃。先试玩并调手感，再进入编辑器开发。

阶段 B：手绘赛道。
完成条件：用真实鼠标输入画出一条有效赛道并开车；开放线、交叉线、过紧弯道有清楚反馈；取消和重画正常，坐标缩放正确。

阶段 C：计时与存档。
完成条件：有效完成一圈才更新纪录；切内场和反向跨线不能刷纪录；暂停、重置及赛道变化正确处理；刷新页面后恢复有效赛道及匹配成绩。

阶段 D：完整视觉与反馈。
完成条件：画面接近参考图确定的纸张、道路、小车和 UI 语言；动态道路与正式素材都参与真实游戏；按钮、提示、粒子、静音操作可用。最终版本不是只有默认矩形的技术样机。

阶段 E：检查与交付。
完成条件：完成下一节的必要检查，修复发现的问题，提供本地启动与操作说明、截图和剩余限制的真实说明。

## 11. 验证要求

测试集中在会影响游戏正确性的逻辑，不为颜色、静态文案或只是复述实现的组件编写机械测试。

建议覆盖这些关键情况：

- 有效闭合路线通过；开放、交叉、退化、非有限数值或道路自重叠的输入被合理拒绝。
- 起点初始化不会记一圈；按顺序完成检查点并正向过线能记圈；反向过线、漏检查点和无效圈不能更新纪录。
- 暂停和重置的计时状态正确，改变赛道后不会错误套用旧纪录。
- 相同持续时间的运动在不同渲染帧率下结果接近，较大时间间隔不会让车辆失控跳跃。
- 存档损坏会恢复默认状态。

使用真实浏览器交互验证以下流程，不只检查页面能打开：

1. 打开默认赛道，点击开始，通过真实按键使车辆前进和转向。
2. 进入编辑模式，用指针画出赛道，开始驾驶；再画一个明显无效的草稿，确认提示和恢复流程。
3. 暂停、继续、R 重置、窗口失焦、刷新恢复都能实际操作。
4. 查看至少 1366×768、1280×800 和较窄桌面窗口；HUD 不遮挡关键驾驶区域，画布、输入和道路判断保持对齐。
5. 检查控制台错误和资源加载失败；检查反复开始、编辑与返回后没有重复事件或明显性能下降。

可以用 Playwright 做适量自动化，再配合实际试玩和截图检查。自动化验证不能只依赖直接修改内部状态来假装完成玩家流程。环境不能执行某项检查时，清楚说明未验证的项目，不声称通过。
